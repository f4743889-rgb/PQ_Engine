# Power Query Engine: зовнішній аудит концепції і відповіді

Дата: 20.10.2026. Стан коду: v4.8 + патчі G, G1 (v4.9 у роботі).

Аудиторові передано лише розділи 1 і 2 документа архітектури (мета і концепція, три шари й потік даних), без дорожньої карти, коду і реєстру запитів. Тому частина рекомендацій уже реалізована, а одна теза спирається на неточне прочитання. Нижче — стислий зміст аудиту, зіставлення з фактичним станом і рішення.

## 1. Висновки аудиту (стисло)

- Концепція обґрунтована: метадані в таблицях, бізнес-правила відокремлено від механізму завантаження, контракт схеми, політики помилок Strict / Report / Lenient, незалежний аудит якості, окрема тестова книга.
- Головний ризик — не кількість функцій, а те, що логічно одне завантаження перетворюється на багато незалежних фізичних обчислень (fn\_ReadSource, fn\_EnforceSchema, fn\_ReadPurpose, генератор схеми, QC Suite). Запити, що посилаються на спільний запит, виконуються незалежно разом із його залежностями; Table.Buffer не ділиться між незалежними обчисленнями.
- Логічна схема: реєстр і затверджена схема → перевірка контракту → нормалізація (один прохід на файл: розбір, фільтр службових рядків, назви, відбір і перейменування, типи, облік помилок) → контроль якості з уже зібраних результатів → бізнес-обробка.
- Відокремити генерацію схеми (каталог колонок для Data Validation) від регулярного завантаження; контроль дрейфу лишити як легку перевірку заголовків.
- Одне правило прийняття завантаження для fn\_EnforceSchema і QualityFlag.
- Розрізняти початкове, канонічне і цільове імена колонок.
- Відсутній файл не має мовчки ставати порожньою таблицею без діагностики.
- Контракт для таблиць конфігурації (ключ (TargetType, SourceColumnName), DataType, конфлікти TargetColumnName, CustomTransform, фільтри); перевірки мають бути дешевими, без читання великих джерел.
- Не ставити Table.Buffer усюди.
- Пріоритети: 1) виявити повторні читання й типізацію; 2) відокремити генерацію схеми; 3) об'єднати перевірки в один прохід; 4) перевірити доцільність матеріалізації; 5) оптимізувати функції за вимірюваннями. Спершу стабілізувати контракт, виміряти, прибрати зайві проходи, потім бізнес-правила.

## 2. Зіставлення з фактичним станом

| Теза аудиту | Стан у Engine |
| --- | --- |
| Незалежні запити повторно виконують спільні залежності; Table.Buffer не ділиться між запитами | **Підтверджено вимірюваннями.** Повторні перегляди в pq\_SchemaDrift, pq\_ExtractedColumns, test\_Summary, test\_Load давали 502 с на тестових файлах (виправлено F2, 34 с). Тести множили читання реальних файлів (виправлено G). Подвійне оновлення зведення в RefreshWithRunLog (виправлено G1). Залишкові випадки — розділ 3 |
| Одне рішення про прийняття для завантаження і QualityFlag | **Реалізовано:** fn\_LoadVerdict (аудит D6, v4.6) |
| Контракт таблиць конфігурації | **Реалізовано:** pq\_SchemaCheck (дублі (TargetType, SourceColumnName), конфлікти цільових назв, DataType, CustomTransform, збіг із метаколонками), pq\_RowFiltersCheck, pq\_RegistryCheck / fn\_RegistryIssues. Файлів не читають |
| Діагностика відсутнього файла | **Реалізовано:** FILE\_ERROR (обов'язковий, блокує), NODATA (необов'язковий), шаблон tblDefaultHeaders лише без шляху (Template, OK) або зі шляхом до недоступного файла (WARN) |
| Три імені колонок | **Неточне прочитання.** fn\_Canon канонізує значення довідників (TargetType, PeriodType), а не назви колонок. Назви колонок порівнюються точно; «регістр відрізняється» в pq\_SchemaDrift — лише підказка. Пара Source → Target: SourceColumnName / TargetColumnName |
| Не ставити Table.Buffer усюди | **Так і зроблено:** правило 6.12 документа архітектури — буфер лише для входу, який переглядається кілька разів, і не для таблиць із клітинками-помилками |
| Спершу вимірювати | Профайлер (ProfilePowerQueries) і журнал запусків (RefreshWithRunLog) є з v4.8 |

## 3. Прийняті до роботи

| № | Дія | Обґрунтування | Стан |
| --- | --- | --- | --- |
| R1 | Генерацію каталогу колонок (tblSchemaColumns / pq\_ExtractedColumns, можливо pq\_SchemaIssues) виключити з «Оновити все», оновлювати окремим макросом на вимогу | Каталог потрібен лише при зміні джерел чи схеми; Excel-файли для нього читаються повністю. pq\_SchemaDrift лишається легкою перевіркою заголовків | Заплановано (першим, дешево й безпечно) |
| R2 | Один розбір файла всередині fn\_RowReport / fn\_SchemaReport | Звіт Report читав ~2× розміру файла (спостереження v4.3) | Спершу виміряти, де другий розбір |
| R3 | Завантаження (q\_…) і звіт якості (qc\_Reports) — два незалежні обчислення того самого файла | Excel не передає готовий результат між запитами, крім таблиці на аркуші / моделі даних. Вибір: якість завжди або лише на вимогу (RefreshWithRunLog перед завантаженням) | Рішення користувача після вимірювань у робочій книзі |

Не прийнято: окрема канонізація назв колонок (назви файлів навмисно чутливі до регістру; див. розділ 6.9 документа архітектури).
