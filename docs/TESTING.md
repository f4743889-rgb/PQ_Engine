## 2. Як запустити

Порядок підготовки тестової книги з репозиторію — у [tests/README.md](../tests/README.md) (SetupTestEngine → Оновити все → аркуш «Тести», таблиця test_All). Тестова книга тримається поза репозиторієм; ExportPowerQueriesToRepo у ній зупиняється.

## 3. Як test_All відрізняє успіх від невиконаного тесту

test_All (`tests/queries/test_All.pq`) для кожного набору рахує Checks (кількість перевірок) і Failed:
- набір, що впав з помилкою, дає `Checks = 0, Failed = 1` і текст у колонці Error;
- **Result = PASS лише якщо `Failed = 0` і `Checks > 0`**: порожній набір чи невиконаний запит — це FAIL, а не PASS.

Усередині наборів пропущена перевірка теж видна: test_HeadersConsistency (з v4.15) дає рядок для кожного SourceID з tblTestExpected — PASS, FAIL, SKIP (файл не читається; Pass лише якщо так і очікується) або NOT_ACTIVE (вимкнене джерело; Pass лише для Status = ABSENT).

## 6. Механізми, на які спирається узгодженість

| Механізм | Де | Що гарантує |
| --- | --- | --- |
| Одне правило зупинки | fn_LoadVerdict — викликають і fn_EnforceSchema (завантаження), і fn_RowReport (QualityFlag) | Звіт якості й завантаження приймають рішення одним кодом |
| Одні налаштування | fn_EffectiveSettings (реєстр → cfgSettings; options не враховуються) | ErrorPolicy, ErrorThreshold, Culture однакові для звіту і завантаження |
| Один конвеєр | fn_ApplyRulesEx — і в звіті (fn_SchemaReport), і в завантаженні (fn_ApplyRules → fn_EnforceSchema) | Відсікання рядків, NonEmpty, перейменування, типи однакові |
| Одне відкриття файла | fn_ResolveSource — помилки доступу повертаються як дані (ErrorCode), а не ламають звіт | Звіт якості не падає через один поганий файл |
| Правило трьох видів запитів | architecture.md, розділ 5 | Немає Formula.Firewall |
| Тести рахують лише свої джерела | fn_QcReports(config, sourceIds) з SourceID із tblTestExpected | Реальні джерела не впливають на результат тестів |
| Дублікати заголовків | fn_ParseSource підвищує перший рядок сам (CSV і аркуші Excel однаково) і зберігає сирі значення в метаданих (RawHeaders); fn_SchemaReport бачить повтори за ними, а не за суфіксом «_1» | Законні «A» і «A_1» не дають хибного дубля (C18), справжній дубль виявляється (C09) |

Узгодженість «QualityFlag ↔ результат завантаження» перевіряється двічі: test_Summary і test_Load звіряють обидва з очікуваннями на тих самих фікстурах, а test_FlagVsLoad (v4.15) — безпосередньо одне з одним (FAIL ⇔ ERROR).

## 8. Ручні перевірки макросів VBA

| Перевірка | Очікування |
| --- | --- |
| ExportPowerQueriesToRepo після імпорту з репозиторію | у GitHub Desktop **немає змін** (книга = репозиторій) |
| ExportPowerQueriesToRepo у тестовій книзі | зупиняється з поясненням |
| UpdateHelp | «Таблиць з порушеннями: 0»; hlpProject без змін, якщо код правил не змінювався |
| SetupTestEngine з кореня клону | у вікні «(репозиторій)»; без .pq або без test_All — зупинка з помилкою |
| RefreshWithRunLog | «Оновити все», потім окреме оновлення pq_QualitySummary; рядки в tblRunLog |
| ProfilePowerQueries | Seq, живлення в Notes; попередження на батареї |

## 9. Продуктивність

Методика і всі заміри — `docs/architecture.md`, розділ 6.12: лише від мережі в режимі найкращої продуктивності; розкид між запусками ±20–30%; варіанти порівнювати в одному запуску профайлера **в обох порядках** (ефект порядку ~13%).
